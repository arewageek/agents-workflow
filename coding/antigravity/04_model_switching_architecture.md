# Antigravity Architecture: Model Switching and Token Exhaustion

This document explains the architectural mechanics of what happens when a conversation hits a token limit (or rate limit) on one model and the user switches to a different model (e.g., from Gemini 1.5 Pro to Gemini 1.5 Flash, or to an Anthropic/OpenAI provider).

To understand this transition, you must grasp the concept of the **"Stateless Brain Transplant."**

---

## 1. The Core Principle: Memory Lives on Disk, Not in the Cloud

As detailed in previous documents, the inference engine (the AI model) is entirely stateless. It has zero permanent memory of your conversation. 

All memory is stored locally on your hard drive in your IDE's `brain/` directory. The illusion of a continuous conversation is maintained because your IDE re-uploads the entire conversation history (the massive JSON array) to the server every single time you press send.

**Therefore, the "Agent" is actually your local IDE. The LLM is just a swappable CPU.**

---

## 2. The Mechanics of the Switch and Schema Translation

When your token limit expires on Model A, and you switch the drop-down in your IDE to Model B, the IDE must perform a rapid, complex translation of the entire history payload before sending it. 

### Step 1: The API Reroute
Your local IDE updates its internal configuration. Instead of pointing its outbound HTTP requests to the `Model A` endpoint (e.g., `generativelanguage.googleapis.com`), it points them to the `Model B` endpoint (e.g., `api.anthropic.com`).

### Step 2: The Universal Translation Layer (Tool Schemas)
Different AI providers use entirely different JSON schemas for defining tools and formatting conversation history. The IDE acts as a universal translator. It takes its internal cached memory array and rebuilds it to match the strict API requirements of the new model. 

*(See the Appendix below for the exact JSON structural differences the IDE must translate).*

### Step 3: The "Cold Start" Coma
The IDE blasts the translated 100,000-token payload over the wire to Model B.
Model B wakes up. From its perspective, it feels like it just woke up from a coma with someone else's memories implanted in its head. It has to instantly speed-read the entire translated history of the conversation in a single inference pass (usually taking under 800 milliseconds) to catch up on what "it" has been doing for the last 4 hours.

---

## 3. The Continuity Illusion (No Special Handoff Instructions)

You might assume that when a switch occurs, the IDE attaches a special system prompt telling the new model, *"Hey, you are taking over for Gemini."* 

**This does not happen. There are zero special instructions attached during a model switch.**

The new model is completely unaware that it is a replacement. The IDE simply formats the JSON history array so that all of Model A's previous replies are labeled as `role: "assistant"` or `role: "model"`. 

Because of how LLMs are programmed, when Model B reads this JSON array, it fundamentally assumes that *it* wrote all of those past responses. It adopts the entire history as its own organic memory. It does not know a transplant occurred. It just picks up exactly where the last `role: "user"` message ended.

---

## 4. The Cognitive and Behavioral Consequences

While the core data history remains identical, the *brain* processing that data has completely changed. This causes immediate, observable shifts in the agent's behavior.

### A. Behavioral Drift (Personality Shift)
Different models have different underlying neural weights, different RLHF (Reinforcement Learning from Human Feedback) training, and different attention mechanisms.
- **Model A (e.g., a "Pro" model)** might have spent the last 10 turns being highly analytical, cautious, and asking clarifying questions before running commands.
- **Model B (e.g., a "Flash" model)** reads that exact same history, but its internal weights make it more impulsive and action-oriented. In the very next turn, Model B might suddenly execute three parallel `run_command` tools without asking permission, completely breaking the established behavioral pattern.

### B. Attention Mechanism Variances ("Lost in the Middle")
Different models suffer from the "Lost in the Middle" attention decay differently.
If you switch models, the new model might suddenly "notice" a piece of code buried in the middle of the context window that the previous model had been ignoring. Conversely, it might suddenly "forget" a strict system rule that the previous model was adhering to perfectly.

---

## 5. The Checkpoint Inheritance

If the conversation is very long, it is highly likely that a `{{ CHECKPOINT }}` (amnesia event) was already generated by the IDE to save tokens while you were using Model A.

When you switch to Model B, Model B inherits this summarized Checkpoint text. 
**Model B has absolutely no way of knowing what was deleted to create that Checkpoint.** It cannot query Model A to ask for the missing details. If Model B needs to see the raw code that was deleted prior to the Checkpoint, it must generate a brand new `view_file` tool call to re-read your local hard drive.

# APPENDIX: The Exact Literal Payload Translation Structure

When you switch from one provider to another, the IDE must completely restructure the outbound JSON payload because Google, Anthropic, and OpenAI do not share a universal API standard. 

Here is exactly how the IDE restructures the data during a model switch:

### Before the Switch (e.g., Outbound to Google Gemini)
The IDE maps tools and history using Google's specific `functionDeclarations` and `parts` array syntax:

```json
{
  "model": "models/gemini-1.5-pro",
  "tools": [
    {
      "functionDeclarations": [
        {
          "name": "view_file",
          "description": "View the contents of a file...",
          "parameters": {
            "type": "OBJECT",
            "properties": {
              "AbsolutePath": { "type": "STRING" }
            }
          }
        }
      ]
    }
  ],
  "contents": [
    {
      "role": "user",
      "parts": [{ "text": "<ADDITIONAL_METADATA>...</ADDITIONAL_METADATA>\nCan you look at payment.ts?" }]
    },
    {
      "role": "model",
      "parts": [
        {
          "functionCall": {
            "name": "view_file",
            "args": { "AbsolutePath": "/Users/username/.../payment.ts" }
          }
        }
      ]
    }
  ]
}
```

### After the Switch (e.g., Outbound to Anthropic Claude / OpenAI style)
The IDE intercepts the switch command, tears down the Google JSON structure, and re-compiles the exact same memory history into the new provider's required syntax (e.g., `tools` with `input_schema`, and `messages` array):

```json
{
  "model": "claude-3-5-sonnet",
  "tools": [
    {
      "name": "view_file",
      "description": "View the contents of a file...",
      "input_schema": {
        "type": "object",
        "properties": {
          "AbsolutePath": { "type": "string" }
        }
      }
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": "<ADDITIONAL_METADATA>...</ADDITIONAL_METADATA>\nCan you look at payment.ts?"
    },
    {
      "role": "assistant",
      "tool_calls": [
        {
          "id": "call_9876xyz",
          "type": "function",
          "function": {
            "name": "view_file",
            "arguments": "{\"AbsolutePath\": \"/Users/username/.../payment.ts\"}"
          }
        }
      ]
    }
  ]
}
```

### The Invisible Bridge
The IDE must perform this exact structural translation for *every single message* and *every single tool execution* in the history array (often numbering in the hundreds of thousands of tokens) before firing the request to the new model. 

The new model receives this translated JSON block, processes the entire history array, and generates its next response natively in its own format. The IDE then catches that response, translates it back into the local Antigravity system state, and displays the text to you, perfectly preserving the continuous illusion.
